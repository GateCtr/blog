In late 2024, a startup's AI-powered research assistant got stuck in an agent loop while the team slept. By the time anyone noticed, the agent had made 47,000 API calls over six hours and racked up $31,000 in LLM charges — roughly 8x their monthly budget. There was no hard cap in place. There was no alert. There was just the invoice.

This is not an unusual story. As AI agents become more autonomous and more deeply embedded in production systems, the absence of proper budget controls is not a minor oversight — it is an operational liability.

This guide explains the three-layer budget control architecture that prevents incidents like this, how to implement each layer, and how to automate enforcement without building the infrastructure yourself.

## The Three Layers of Budget Control

A robust budget control system has three distinct layers, each serving a different purpose:

```
Layer 1: Rate Limits     — Control velocity (requests per minute/hour)
Layer 2: Soft Alerts     — Early warning system (notify at 70%, 90%)
Layer 3: Hard Caps       — Absolute ceiling (block at 100%)
```

You need all three. Rate limits alone will not stop a sustained cost event. Hard caps alone give you no warning. Soft alerts alone are only useful if someone acts on them.

## Layer 1: Rate Limits

Rate limits control how fast money can be spent, not how much in total. They are your first line of defense against runaway agents and infinite loops.

The right granularity depends on your architecture:

- **Per-user rate limits**: For platforms where end users trigger LLM calls. Prevents any single user from consuming a disproportionate share of capacity.
- **Per-agent rate limits**: For autonomous agents. A well-behaved agent should never need more than a few hundred calls per hour.
- **Per-endpoint rate limits**: For API endpoints that call LLMs. Prevents a traffic spike from becoming a cost spike.

```python
import time
import asyncio
from collections import defaultdict
from dataclasses import dataclass, field

@dataclass
class RateLimiter:
    """Token bucket rate limiter for LLM requests."""
    max_requests_per_minute: int
    _buckets: dict = field(default_factory=lambda: defaultdict(list))

    def is_allowed(self, entity_id: str) -> tuple[bool, float]:
        """
        Check if entity_id is within rate limit.
        Returns (allowed, retry_after_seconds).
        """
        now = time.time()
        window_start = now - 60  # 1-minute window

        # Clean old entries
        self._buckets[entity_id] = [
            t for t in self._buckets[entity_id] if t > window_start
        ]

        if len(self._buckets[entity_id]) >= self.max_requests_per_minute:
            oldest = self._buckets[entity_id][0]
            retry_after = 60 - (now - oldest)
            return False, retry_after

        self._buckets[entity_id].append(now)
        return True, 0.0

# Usage
limiter = RateLimiter(max_requests_per_minute=60)

def call_llm_with_rate_limit(user_id: str, prompt: str):
    allowed, retry_after = limiter.is_allowed(user_id)
    if not allowed:
        raise RateLimitError(f"Rate limit exceeded. Retry after {retry_after:.1f}s")
    return llm_client.complete(prompt)
```

## Layer 2: Soft Alerts

Soft alerts are your early warning system. They notify the right people at spending thresholds — before the hard cap is hit — giving you time to investigate and respond.

Effective alert thresholds:

- **70% of budget**: Informational. Worth knowing, probably fine.
- **85% of budget**: Attention required. Investigate the trend.
- **95% of budget**: Urgent. Prepare to act or extend the budget.

The alerts should go to the people who can act on them — the engineering lead and the person who manages the LLM budget. Not to a generic alert channel that gets ignored.

A good alert includes:

```python
import httpx
from datetime import datetime, UTC

async def send_budget_alert(
    team_id: str,
    current_spend: float,
    budget_cap: float,
    period: str = "monthly"
) -> None:
    """Send a Slack webhook alert when spend crosses a threshold."""
    pct = (current_spend / budget_cap) * 100
    urgency = "warning" if pct < 90 else "danger"

    message = {
        "attachments": [{
            "color": "#FF9900" if urgency == "warning" else "#FF0000",
            "blocks": [
                {
                    "type": "section",
                    "text": {
                        "type": "mrkdwn",
                        "text": (
                            f"*LLM Budget Alert — {team_id}*\n"
                            f"*Spend:* ${current_spend:,.2f} / ${budget_cap:,.2f} "
                            f"(*{pct:.1f}%* of {period} budget)\n"
                            f"*Time:* {datetime.now(UTC).strftime('%Y-%m-%d %H:%M UTC')}\n"
                            f"{'⚠️ Approaching limit — investigate now.' if urgency == 'warning' else '🚨 Critical — immediate action required.'}"
                        )
                    }
                }
            ]
        }]
    }

    async with httpx.AsyncClient() as client:
        await client.post(SLACK_WEBHOOK_URL, json=message)
```

The key requirement: alerts must include **which team or project** is driving the spend and **whether it is a spike or a trend**. An alert that just says "you have spent $4,200" is not actionable. An alert that says "the customer-chat team has spent $4,200 this month, up from $1,800 at this point last month, driven by a 3x increase in average tokens per request in the last 48 hours" — that is actionable.

## Layer 3: Hard Caps

Hard caps are non-negotiable spending limits. When a hard cap is reached, requests fail. This is your last line of defense, and it should fail loudly — returning a clear error that the application can handle gracefully.

```python
import asyncio
from decimal import Decimal

class BudgetExceededError(Exception):
    def __init__(self, team_id: str, current: float, cap: float):
        self.team_id = team_id
        self.current = current
        self.cap = cap
        super().__init__(
            f"Budget cap exceeded for {team_id}: "
            f"${current:.2f} used of ${cap:.2f} limit"
        )

async def check_and_reserve_budget(
    team_id: str,
    project_id: str,
    estimated_tokens: int,
    model: str
) -> None:
    """
    Check budget and reserve capacity for a request.
    Raises BudgetExceededError if any limit would be exceeded.
    Handles hierarchical limits: project → team → org.
    """
    estimated_cost = estimate_cost(estimated_tokens, model)

    # Check all levels atomically to prevent race conditions
    async with db.transaction():
        levels = [
            ("project", project_id),
            ("team", team_id),
            ("org", await db.get_org_id(team_id)),
        ]

        for level, entity_id in levels:
            current = await db.get_current_spend(entity_id, period="monthly")
            cap = await db.get_hard_cap(entity_id)

            if cap and (current + estimated_cost > cap):
                raise BudgetExceededError(entity_id, current, cap)

        # Reserve the estimated cost to prevent concurrent over-spend
        for _, entity_id in levels:
            await db.increment_reserved(entity_id, estimated_cost)

def estimate_cost(tokens: int, model: str) -> float:
    """Estimate cost based on token count and model pricing."""
    PRICING = {
        "gpt-4o": 0.005,           # per 1K tokens
        "gpt-4o-mini": 0.00015,
        "claude-3-5-sonnet": 0.003,
        "gemini-1.5-flash": 0.000075,
    }
    rate = PRICING.get(model, 0.005)  # default to GPT-4o pricing
    return (tokens / 1000) * rate
```

Note the `async with db.transaction()` block — budget checks must be atomic. A naive implementation that reads current spend and then writes an update can allow concurrent requests to both "pass" the budget check and collectively exceed the cap. This is a common bug in hand-rolled implementations.

## Granularity: Budget Controls at Every Level

Budget controls are most useful when they can be applied at multiple organizational levels simultaneously:

| Level | Use case |
|-------|----------|
| **Organization** | Total monthly ceiling across all teams |
| **Team** | Per-team allocation; prevents one team crowding out others |
| **Project** | Per-application budget; useful for multi-product companies |
| **User** | Per-user limits for B2C products where end users trigger LLM calls |
| **Agent** | Per-agent limits for autonomous AI systems |

A correctly implemented hierarchical system enforces all levels simultaneously: a request that would put a user, project, or team over any of their respective limits is blocked, even if the org-level budget has headroom.

## Frequently Asked Questions

### What should I do if the hard cap is hit and it is a legitimate production outage?

Design your application to degrade gracefully when budget is exceeded. Return cached responses where possible, show a maintenance message, or fall back to a non-LLM code path. The hard cap should never cause a silent failure — the application should detect the `BudgetExceededError` and handle it explicitly.

### How do I set the right cap value?

Start with 2x your current average monthly spend. This gives you room for organic growth without constant cap adjustments, while still protecting against runaway cost events (which typically spike to 5–10x normal spend). Adjust the cap after three months once you have a stable baseline.

### Can I temporarily increase a cap without a code change?

With a gateway approach, yes — you update the configuration through the dashboard or API. With a self-built system, it depends on how you stored the cap values. Hard-coded caps in application config require a deployment; database-stored caps can be updated without one. Always use the latter in production.
