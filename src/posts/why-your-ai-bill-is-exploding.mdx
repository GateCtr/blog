On a Tuesday morning, a startup's engineering lead opened their OpenAI dashboard to check on a new agent feature they had shipped the previous week. The bill for a single day was $12,400. Their monthly budget was $8,000. By the time they found the bug — an agent that retried failed requests without a backoff limit — the week was nearly over.

This kind of incident is not rare. It is, in various forms, one of the most common production AI horror stories. The good news: every version of this story has a finite set of root causes, and each one has a concrete fix.

Here are the five reasons AI bills explode, and exactly what to do about each.

## Reason 1: Agent Loops with No Hard Cap

An agent that encounters an error does not stop — it retries. If the retry logic has no limit, and the error condition is persistent (wrong API key, a service that is down, a misconfigured tool), the agent will loop indefinitely, making API calls until something external stops it.

Without a hard budget cap, "something external" is you waking up and checking the dashboard.

**The fix: implement a hard budget cap that blocks requests the moment it is hit.**

```python
import asyncio

HARD_CAP_USD = 200.00  # Daily cap per agent

async def budget_checked_call(agent_id: str, messages: list[dict]) -> str:
    from openai import OpenAI, RateLimitError
    
    current_spend = await db.get_daily_spend(agent_id)
    
    if current_spend >= HARD_CAP_USD:
        raise RuntimeError(
            f"Agent {agent_id} has hit its daily cap (${HARD_CAP_USD}). "
            "Request blocked. Reset at midnight UTC."
        )
    
    client = OpenAI()
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages
    )
    
    cost = estimate_cost(response.usage, "gpt-4o-mini")
    await db.increment_daily_spend(agent_id, cost)
    
    return response.choices[0].message.content

def estimate_cost(usage, model: str) -> float:
    rates = {"gpt-4o-mini": (0.00015, 0.0006), "gpt-4o": (0.005, 0.015)}
    inp_rate, out_rate = rates.get(model, (0.005, 0.015))
    return (usage.prompt_tokens * inp_rate + usage.completion_tokens * out_rate) / 1000
```

Also: configure the hard cap at the infrastructure level, not just in application code. If a bug bypasses your check, the infrastructure cap is the safety net.

## Reason 2: Context Accumulation

Prompts grow. A system prompt that started at 200 tokens after six months of iteration is often 2,000+ — loaded with edge cases, defensive instructions, and examples that were added one at a time and never reviewed as a whole.

Conversation history is worse. An application that sends full chat history on every request is paying linearly for each turn. A 20-turn conversation at 500 tokens per turn costs 10,000 input tokens per request — just for the history.

**The fix: audit and trim.**

```python
import tiktoken

def audit_context_cost(messages: list[dict], model: str = "gpt-4o") -> None:
    enc = tiktoken.encoding_for_model(model)
    pricing = {"gpt-4o": 5.0, "gpt-4o-mini": 0.15}
    rate = pricing.get(model, 5.0)
    
    print(f"\n{'Role':<12} {'Tokens':>8} {'Cost/req':>12}")
    print("-" * 36)
    
    total = 0
    for msg in messages:
        tokens = len(enc.encode(msg.get("content", "")))
        cost = tokens * rate / 1_000_000
        print(f"{msg['role']:<12} {tokens:>8,} {'$'+f'{cost:.5f}':>12}")
        total += tokens
    
    total_cost = total * rate / 1_000_000
    print(f"\nTotal: {total:,} tokens → ${total_cost:.4f} per request")
    print(f"At 100K requests/day: ${total_cost * 100_000:.0f}/day")
```

Then implement sliding history (keep only the last 4–6 turns) and trim your system prompt aggressively.

## Reason 3: GPT-4o for Everything

The default model selection strategy for most teams is: use GPT-4o. It is the most capable, so it is the safe choice. The problem is that it is also the most expensive choice — 33x more expensive than GPT-4o mini on input tokens.

For tasks like classification, entity extraction, intent detection, JSON formatting, and short summarization, GPT-4o mini produces output that is indistinguishable from GPT-4o. Using it costs 97% less.

**The fix: audit your request types and route accordingly.**

Evaluate with 200 real samples before rolling out. For classification tasks, you will almost certainly find no meaningful quality difference.

## Reason 4: No Per-Request Visibility

Monthly dashboards show you a number. They do not show you which feature or endpoint is responsible, whether cost per request is trending up, or which user triggered a spike at 3 AM.

Without per-request visibility, you cannot optimize what you cannot see — and you cannot detect anomalies before they become expensive.

**The fix: log cost metadata on every LLM call.**

```python
import logging, time

logger = logging.getLogger("llm_costs")

def instrumented_call(
    messages: list[dict],
    model: str,
    endpoint: str,
    user_id: str | None = None
) -> str:
    from openai import OpenAI
    client = OpenAI()
    
    start = time.monotonic()
    response = client.chat.completions.create(model=model, messages=messages)
    latency_ms = (time.monotonic() - start) * 1000
    
    usage = response.usage
    rates = {"gpt-4o": (5.0, 15.0), "gpt-4o-mini": (0.15, 0.60)}
    inp_rate, out_rate = rates.get(model, (5.0, 15.0))
    cost = (usage.prompt_tokens * inp_rate + usage.completion_tokens * out_rate) / 1_000_000
    
    logger.info("llm_request", extra={
        "endpoint": endpoint,
        "model": model,
        "user_id": user_id,
        "input_tokens": usage.prompt_tokens,
        "output_tokens": usage.completion_tokens,
        "cost_usd": round(cost, 6),
        "latency_ms": round(latency_ms, 1),
    })
    
    return response.choices[0].message.content
```

Pipe these logs to your data warehouse. Build a weekly report: average cost per request by endpoint. An upward trend here is always a signal worth investigating.

## Reason 5: Provider Price Changes You Missed

OpenAI has changed model pricing multiple times. Anthropic has changed pricing. Google has changed pricing. If you have not reviewed your cost assumptions in the past three months, your cost model may be based on outdated numbers.

This matters because the optimization decisions you made six months ago — which model to use for which task — may not reflect current pricing realities. A model that was expensive then may now be the cheapest option for its task tier.

**The fix: schedule a quarterly pricing review.** Pull current prices from each provider's pricing page, update your routing policies, and re-run your cost model.

## Frequently Asked Questions

### How do I set a hard budget cap on OpenAI?

OpenAI provides monthly and notification limits at the account level under Settings → Billing → Usage limits. These are account-wide, not per-project or per-user. For granular per-project or per-user limits, you need to implement them in your application code (as shown above) or use a gateway that enforces them at the infrastructure level.

### What caused my bill to spike suddenly?

The most common causes, in order of frequency: (1) an agent loop or retry storm — check your per-request volume in the OpenAI usage dashboard, broken down by hour; (2) a new feature that uses a more expensive model than intended; (3) a context window that grew significantly — check average input tokens per request over the past 30 days. A spike in request volume is easy to see; a gradual increase in tokens per request is harder to spot and more insidious.
