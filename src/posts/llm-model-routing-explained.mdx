The fastest way to reduce LLM spend is also the most underused: routing each request to the cheapest model that can handle it well. It sounds obvious. In practice, most teams never implement it — not because they disagree with the principle, but because building and maintaining routing logic is genuinely tedious.

This article explains how model routing works, what makes it difficult to implement correctly, and why the best teams delegate it to infrastructure rather than application code.

## Why Model Choice Matters More Than You Think

The pricing gap between frontier models and capable smaller models has widened dramatically over the past two years. In 2026, the difference is not marginal — it is one to two orders of magnitude.

If 60% of your production requests are simple classifications or short extractions, routing them to GPT-4o mini instead of GPT-4o cuts the cost of those requests by 97%. At scale, that is not a rounding error — it is the difference between a $10,000 monthly bill and a $4,000 one.

## What Routing Decisions Are Based On

Good routing decisions combine several signals:

### Task type

The most reliable routing signal. Classification, entity extraction, short summarization, and intent detection are all tasks that small models handle well. Open-ended generation, complex multi-step reasoning, code generation in complex codebases, and nuanced content requiring judgment benefit from larger models.

### Prompt complexity

A short, well-structured prompt with a clear task is more likely to be handled correctly by a smaller model. A long, ambiguous prompt with multiple sub-tasks is a signal to route up.

### Required output quality

For internal tooling — data pipelines, internal search, admin automation — a slightly lower quality bar is usually acceptable. For customer-facing features, you want the best output the task requires.

### Latency requirements

Smaller models are faster. If a feature requires sub-500ms response times, the model selection is constrained regardless of cost.

## The Routing Flow

A request goes through the router before it reaches any model:

```
Application → Gateway → [Task Classifier] → Model Selection → Provider API
                              ↓
                    [Quality Monitor] ← Response
                              ↓
                    Route up if quality threshold not met
```

The classifier analyses the incoming request and assigns it to a complexity tier. The router selects the cheapest model in that tier. If the response quality falls below a configured threshold, the gateway retries with the next tier up — transparently, without the application knowing.

## Implementing a Basic Router Yourself

Here is what a manually maintained router looks like in practice:

```python
import openai
from dataclasses import dataclass
from enum import Enum

class ComplexityTier(Enum):
    SIMPLE = "simple"
    MODERATE = "moderate"
    COMPLEX = "complex"

MODEL_MAP = {
    ComplexityTier.SIMPLE: "gpt-4o-mini",
    ComplexityTier.MODERATE: "claude-3-5-sonnet-20241022",
    ComplexityTier.COMPLEX: "gpt-4o",
}

SIMPLE_TASK_TYPES = {"classify", "extract", "summarize_short", "intent_detect"}
COMPLEX_TASK_TYPES = {"code_generation", "analysis", "reasoning", "synthesis"}

def classify_complexity(prompt: str, task_type: str) -> ComplexityTier:
    if task_type in SIMPLE_TASK_TYPES and len(prompt) < 800:
        return ComplexityTier.SIMPLE
    elif task_type in COMPLEX_TASK_TYPES or len(prompt) > 4000:
        return ComplexityTier.COMPLEX
    else:
        return ComplexityTier.MODERATE

def route_request(prompt: str, task_type: str) -> str:
    tier = classify_complexity(prompt, task_type)
    return MODEL_MAP[tier]

# Usage
model = route_request(user_prompt, detected_task_type)
response = openai.chat.completions.create(model=model, messages=[...])
```

This works for simple cases. The problems emerge quickly in production:

- Model lists go stale as providers update pricing and capabilities
- Quality thresholds require manual calibration per task type
- Fallback logic — what happens when a model is unavailable? — adds complexity
- Routing decisions are invisible: you cannot see which requests went where and why
- The classifier itself needs maintenance as your product evolves

## Frequently Asked Questions

### Can I override the router for specific requests?

Yes. You can pin specific requests to a model by passing the model name explicitly instead of `"auto"`. This is useful for features where you have tested a specific model and want predictable behavior regardless of the routing policy.

### What happens if the selected model is unavailable?

The router falls back to the next capable model in the tier, then to the tier above if needed. Provider outages are handled transparently — your application receives a valid response without knowing which model ultimately handled the request.
